# Data requirements for the liquidity forecasting system

This document lists the data the model needs, where it comes from, how far back to
pull it, and the exact table layouts the code accepts (`liquidity_forecast/schema.py`).
Loaders for the common source formats are in `liquidity_forecast/loaders.py`; sample
files in every supported format are in `sample_source_files/` (generated by
`run_demo_real_data.py`) and can be handed to feed owners as format examples.

## 1. Summary: depth and grain

| Data family | Minimum | Target | Grain to store |
|---|---|---|---|
| Balances | 15 months | 3 years | Every observation (EOD + intraday snapshots) |
| Transactions | 15 months | 3 years | Event level |
| Known-future flows (FX, MM, securities, standing orders, CLS) | 15 months | 3 years | Point-in-time: as known on each day |
| Queue snapshots / release decisions | whatever exists | 12+ months, start capturing now | ≤ 15 min snapshots |
| Treasury actions (sweeps, funding trades) | same as transactions | 3 years | Event level, tagged |
| Market data | 3 years | 5 years | Daily or intraday |
| Calendars, cut-offs, events | full | full | As-of dated rules |
| Reference data (accounts, lines, limits) | full lifetime | full lifetime | With change history |
| Desk forecasts (benchmark) | 12 months | 3 years | Each forecast with origin + target time |

Three years covers three year-ends, twelve quarter-ends, and at least one stress
episode. Fifteen months is the floor: one full annual cycle plus a test window.

## 2. Canonical tables

All timestamps tz-naive in one reference zone (the treasury centre's local time).
Amounts signed from the account's viewpoint: `+` credit, `−` debit.

## 3. Source systems → tables

| Source | Format | Table(s) | Loader | Notes |
|---|---|---|---|---|
| Nostro statements | MT940 / MT950 | balances (opening, booked, available at EOD), transactions (value-dated lines) | `load_mt940` | Lines carry a date only; use for accounts with no intraday feed |
| Intraday reports | MT942 | transactions (timed by `:13D:`), balances if the agent sends one | `load_mt942` | Best intraday source for nostros |
| ISO statements/reports | camt.053 / camt.052 | balances (CLBD, CLAV, OPBD, ITBD/ITAV), transactions (`Ntry`) | `load_camt` | `BookgDt/DtTm` gives intraday timing when present |
| Payment hub / GL cash | CSV / parquet | transactions | `load_payment_hub` | Intraday source of truth for all accounts; supply `column_map` and `product_map` |
| RTGS statements (Fed account, T2 ICM) | CSV export / camt | balances, transactions | `load_camt` or `load_payment_hub` | Central bank balance incl. reserve position |
| FX blotter | CSV | scheduled_flows (two legs per trade) | `load_fx_blotter` | `known_at` = trade time; set `settlement_hour` per currency |
| MM deposits/loans, securities pipeline, standing orders, salary/tax files, CLS pay-in schedule | CSV | scheduled_flows | `load_scheduled_flows` | One call per flow type |
| Liquidity manager queue | CSV | queue_snapshots | `load_queue_snapshots` | |
| TMS / desk cash forecast history | CSV | benchmark | `load_benchmark` | |
| Market data vendor, FRED, ECB SDW, BoE | CSV | external | `pandas.read_csv` | |

Combine step: `combine_balances()` picks the preferred `balance_kind` per (account, time)
and `combine_transactions()` de-duplicates lines that appear in both EOD and intraday
feeds, keeping the intraday timestamp.

## 4. The `flow_class` tag — the most important field

The model's target must exclude flows that are decisions or already known:

| flow_class | meaning | examples | treatment |
|---|---|---|---|
| `client` | unscheduled, externally driven | client wires, ACH, incoming counterparty payments | predicted |
| `known` | settled flows that were in `scheduled_flows` beforehand | FX legs, maturities, coupons | added from `scheduled_flows`; the residual (late, short, cancelled) is predicted |
| `treasury` | the desk's own liquidity actions | sweeps, funding transfers, funding FX swaps, repo cash | excluded from target and actuals (`DataConfig.exclude_flow_classes`) |
| `fee` | charges, interest | | predicted (small) |
| `internal` | book transfers between own accounts that net to zero | | predicted or excluded per policy |

Map from your source codes with `LoaderConfig.flow_class_map` (SWIFT `NSWP`, `NTRS`,
hub product codes). If the hub can tag "initiated by treasury desk" directly, use that.

## 5. Point-in-time rules

* `scheduled_flows` must hold what was known **at `known_at`**, not the corrected final
  version. Amendments are new rows; cancellations set `cancelled_at`.
* Reference data changes (re-purposed accounts, line changes) are applied from their
  effective date, never back-filled.
* Statement corrections and reconciliation adjustments are transactions with their own
  timestamp (the day they were posted), not edits to history.
* `validate_all(strict=True)` rejects `known_at > value_time`.

## 6. Data quality checks on arrival

1. `schema.describe()` — rows, accounts, date range per table; look for gaps.
2. Balance continuity: `balance[t] − balance[t−1] − net_flow[t]` per account should be ~0
   after `flow_class` is complete; large residuals mean missing transactions or a
   balance kind mismatch (booked vs available).
3. `balance_filled_flag` rate per account per day < 5%.
4. Duplicate lines across feeds: check `combine_transactions` log for the de-dup ratio.
5. Time zone: the intraday flow profile (mean scaled flow by hour) should peak where
   your payment cut-offs are; an offset of one hour is a tz/DST error.
